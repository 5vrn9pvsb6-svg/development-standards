# 验证与交付

中文规则源 | [English](../en/verification-and-delivery.md) | 配对修订：`2026-10-05.9`

综合 Google 的有效测试/审查原则、微软的完成条件，以及 AWS 的部署验证思路。检查规模由风险决定，不要求所有任务执行全部检查。出处见 [sources.md](sources.md)。

## 验证选择

正式开发从已确认的验收条件和模块/接口契约选择检查；其他模式按实际改动检查，不因缺少产品文档阻塞。保持“需求 -> 负责模块 -> 验收测试或检查”的可追踪关系；正式开发测试通过不能补偿适用门槛尚未满足。

| 改动 | 需要考虑的证据 |
| --- | --- |
| 文字、注释、格式 | 差异审阅、格式/解析；说明为什么不需要功能测试 |
| 缺陷修复 | 原问题复现、修复后的回归测试、相邻行为检查 |
| 功能/契约变化 | 新行为、边界/失败测试，必要的类型/构建与消费者检查 |
| 数据库设计/变更 | 实际结构、字段语义、约束和索引与设计一致；适用的访问、兼容、迁移及恢复检查 |
| Server 与 Agent 交互 | 新 Server 与约定低版本 Agent 的协议、字段语义及核心流程兼容证据 |
| 行为保持重构 | 重构前后通过的行为保护测试，覆盖异常及副作用；不能只看编译，不要求旧实现失败 |
| 权限/文件/网络/敏感数据 | 合法路径与拒绝路径、安全失败、不会泄漏/越界的测试 |
| 并发/资源/性能 | 竞争、取消/清理、相关负载或性能证据；按适用性运行 |
| UI 行为 | 实际运行，关键交互、适用视口、错误状态与必要的视觉检查 |
| 迁移/部署 | 隔离环境演练、兼容性、部署后健康检查和恢复证据 |

复用现有命令和框架。没有某项工具时，不擅自安装整个工具链；选合理替代或记录未验证项。

### 局部修复的验证与记录

局部修复只减轻文档与重复批准，不减少缺陷验证。依据已明确的预期行为复用或补充能发现原问题的回归用例，运行受影响模块及必要的相邻检查，不为补齐形式要求重复生成测试或运行无关全仓库检查。范围与风险仍需由实际调用、数据流和契约判断，不仅看文件数量。

在当前任务、已有 Issue 或修复说明中关联目标与依据、实际改动位置、测试/检查命令和结果即可，不强制新建映射表或需求/架构文档；数据库相关编码仍按编码阶段规则输出/保存当前范围设计。必要检查未运行、环境阻塞或失败时如实标注，不声称已完成验证；需要正式流程或旧 Agent 兼容证据的改动不能通过这段规则免除门槛。

## 测试有效性

- 缺陷测试应在旧实现上失败、在修复后通过；能安全验证时执行，不能验证时说明，不伪造先前失败结果。
- 检查可观察行为与契约，不只复刻实现细节；必要的交互断言按风险选择。
- 不让 Mock 掩盖目标问题；关键跨模块/外部契约风险不能仅凭全 Mock 单元测试宣布通过。
- 测试结果可重复，失败信息可理解，数据相互隔离；使用合成或脱敏数据。
- 覆盖率是查找缺口的信号，不是正确性证明；仓库没有门槛时不自动要求统一的 80% 或 90%。
- 改动后重新运行必要检查；旧结果不能证明后续编辑正确。

## 失败处理

记录事实、原因假设、下一步验证。用日志/差异收窄修复范围，不无限重复同一命令或扩大改动。

- **本次回归**：修正后重新验证；不得交付成已通过。
- **既有失败**：有基线运行或其他证据才能这样分类，否则标为原因未确认。
- **环境阻塞/未运行**：说明缺少的依赖、权限或服务，以及对结论的限制。
- **不适用**：说明与当前变化无关的理由，不以此掩盖真实检查缺口。

证据不足时交付“已实现但未完成验证”的状态。不要通过跳过用例、移除有效断言、全局禁用检查或关闭安全控制来制造成功结果。

## 代码自审

审阅本次完整差异及相关调用边界：是否符合适用需求/设计或明确的局部修复目标与范围，模块职责是否合理，复杂度是否必要，接口/错误/资源是否清晰，测试能否发现问题，安全输入流是否受控，相关记录是否更新。

按 [编码约定](coding-conventions.md) 检查本次新增/修改的手写源文件职责与实际行数，沿用项目阈值，无约定时检查是否超过 1000 行；核对合理拆分或保留理由，以及生成/锁文件/第三方代码的豁免依据。拆分后检查调用、导入和行为保护，不能用文件变短代替行为验证；未计数或未验证如实说明，不为此扫描/重构无关文件或新建治理工具。

自审不是独立审查。若项目要求其他审阅者、CI 或产品确认，明确待审批状态，不伪造审批或绕过门禁。

## 界面方案与实现一致性

设计阶段实际在浏览器打开三套 HTML 视觉原型，快速核对入口/资源加载、布局比例、配色/字体/间距、组件一致性、视觉层级及目标代表性视口中的可读性、溢出/遮挡。保持需求/页面/数据/视口一致且有实质设计差异，避免只有线框、空占位或换色稿；静态 HTML/CSS 合格，不因按钮未响应或缺少 JS 判失败，默认不逐控件做交互或端到端测试。仅用户明确要求的交互演示按指定范围检查。确认未接真实业务服务，记录仅视觉展示/未实现范围及实际渲染结果。浏览器/权限不可用时报告原型已生成但渲染未验证，不编造视觉检查通过；缺少原型或真实选择时保留待完善/待选择状态。

正式界面实现后，仍须对照用户选中方案的版本和适用范围检查实际布局、信息层级及关键交互；按目标设备运行并保存必要截图/证据，检查适用桌面/移动视口、文本溢出/遮挡、导航、表单及关键空/加载/错误状态、键盘/焦点等可访问性。未运行或未渲染的项说明限制，不能用视觉原型、旧截图或生成稿冒充正式产品验证；原型显示美观或轻量模拟成功都不证明真实服务/数据库/权限行为。交付关联设计选择、实际实现与检查结果；纯诊断不授权保存或修改设计，实际产品代码修改仍须递增产品版本。

## 模块与验收证据闭环

正式开发在既有架构映射表或关联验收记录中，只更新本次已确认范围的实际证据：需求编号、负责模块、实际代码位置、测试用例/检查命令位置、实现状态、验证状态及结果。部分确认时保持其他范围待决/未实施，不将一个范围通过写成整份文档已确认或全部验收。设计阶段写规划路径和验证计划，不能提前标为已实现/已通过；不强制另外创建一套重复台账。

实现状态与验证状态分别记录：已实现但测试未运行是“已实现 / 未运行”，不是“已完成验收”。验证至少区分通过、失败、未运行、不适用；后两者注明原因和影响。一项需求的部分检查通过不能覆盖其未验证验收条件，旧代码版本的结果也不能证明新改动。

核对本次实际调用、导入、数据读写入口与允许依赖是否一致，关注循环依赖、跨层穿透和绕过模块接口。已有依赖/架构测试工具时复用；没有时审阅相关代码和调用者并记录覆盖范围，不自行安装整个治理平台，不把局部自审说成全仓库依赖验证。发现边界或契约必须改变时，返回文档更新和重新确认流程。

确认只保护业务/设计内容。补充实现路径、测试结果或失败说明不改变设计时，不需要重复确认；它们也不能偷偷扩大原确认范围。

## 数据库设计与实现一致性

数据库相关编码先核对是否已输出相关设计要点并保存或复用准确的独立文档，记录路径、内容版本和范围；与实际 SQL、ORM、迁移及可安全检查的结构/约束/索引一致，存在架构引用时同步它。已有数据库记录现状依据及本次差异，不把推断写成事实。保存文档或脚本能执行不代表设计/验收通过；按影响验证访问路径、失败约束、现有数据/消费者兼容以及适用迁移和恢复，记录真实命令、产物和结果。环境或权限不足时说明未验证项，不擅自访问真实数据库或生产数据。

设计差异同步文档及已有引用；已确认范围内的实现细化不增加审批，影响需求、技术栈、公共契约、模块边界或权限/数据规则时才更新并确认受影响内容。查询修复按原目标验证，相关设计也须输出/保存，但只覆盖当前范围，不补整个数据库历史或需求/架构。只读检查不获得文档编辑权限。交付附相关设计路径/版本、实际变化与未验证项，不能用文档齐全替代实际检查。

## 产品版本交付检查

存在项目代码变更时，对照修改前基线，核对受影响产品真实版本入口已按项目规则递增，必要包/构建/显示版本及已有变更记录一致；同一未交付变更已正确升版时不因验证修正或续接再次递增。不能用聊天中的新版本、文档修订或依赖升级替代实际产品版本修改。检查结构化配置可解析，按项目现有方式核对可运行的版本输出或构建元数据；未运行构建/运行时检查时明确限制，不编造一致性结果。

交付报告附旧版本、新版本、版本入口与必要同步项、变化摘要及实际检查结果。无代码变更则无需产品升版。缺少规则、版本编辑授权或必要同步项时报告缺口，不标为完成；升版不是测试通过、已批准、可合并或已发布的证明，不豁免 Bug 回归、安全和低版本 Agent 验证，也不授权标签或发布操作。

## 低版本 Agent 兼容性验证门槛

有客户端 Agent 通信的产品，涉及 Agent 交互的 Server 变更必须遵循 [核心规范](standards.md) 的红线，按已明确的兼容矩阵验证，而不是只测当前最新版 Agent：

- 记录被测 Server 的代码/构建版本、低版本 Agent 的准确版本和产物来源、运行环境、协议及流程场景、实际命令/用例、结果和证据位置。未覆盖的版本或场景明确列出，不用单一通过样本概括全部范围。
- 优先运行真实低版本 Agent 与新 Server 的集成/端到端测试，检查约定的正常及失败流程。按变更影响覆盖字段缺省、默认值、类型/枚举、错误响应和新旧消息解析；旧 Agent 不升级时必须仍能完成既有核心流程。
- 真实历史协议样本和契约测试可以补充边界证据，但不能把样本回放、全 Mock 单测或最新 Agent 测试声称为真实低版本端到端验证。若无法取得足以证明协议及核心流程兼容的证据，记录限制并保持门槛未通过。
- 存在破坏兼容、兼容用例失败、证据缺失或必要验证未运行时，阻断相关合并与发布，不报告“可合并”“可发布”或“兼容已通过”。可交付待审改动和具体阻塞项，不以强制升级 Agent 消除阻塞。
- 合并或发布仍需用户授权及项目既有审批/CI 门禁；兼容测试通过本身不授予执行权限。不因新增此规则擅自修改流水线或部署配置。

纯文字或经影响分析确认不涉及 Agent 交互的改动，可说明该验证项不适用及依据；“只改内部代码”“只改一行”不是跳过检查的理由。新 Server 的协议兼容设计和证据应关联到现有需求/架构记录，不另造重复台账。合格局部修复缺少历史产品文档时，可在修复记录中保留兼容范围、矩阵及实际证据，不为记录位置追补两份文档，也不省略兼容验证。

## 发布要求

仅当用户明确把发布/迁移放入任务范围，且具备必要授权时执行。普通编码任务只交代发布影响，不自动修改部署配置。

生产变更先确定成功信号、观察窗口、失败触发条件和恢复方式；使用项目现有的小批量/分阶段策略。数据或协议变更要确认旧版本兼容性，不能把“回滚代码”当作恢复数据的保证。

自动回滚、Feature Flag、告警和流水线是可选实现手段，按项目条件采用；没有对应权限时提供待执行步骤，不替用户新建生产机制。

## 证据交付

最终报告只列实际有关的内容：当前阶段、目标/改动结果、检查命令和结果、关键未验证项、兼容/安全/恢复风险、必要审批或后续操作。正式开发和产品文档工作附相关文档位置/版本及确认状态，局部修复或行为保持重构给出目标依据、范围与检查结果，不强制提供两份产品文档；其他轻量和只读任务不强制提供这些文件。停留在确认阶段时明确未开始实现；实现后的证据应可定位，但不输出没有真实结果支持的长检查表。
