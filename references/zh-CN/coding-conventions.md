# 编码约定

中文规则源 | [English](../en/coding-conventions.md) | 配对修订：`2026-10-05.9`

## 选择规则

顺序是：仓库明确规范与工具配置、相邻代码和既有框架模式、再到适用的公开参考。不要同时套用相互冲突的 Google、Airbnb 或公司规则。

| 技术场景 | 没有本地约定时的参考 | 使用限制 |
| --- | --- | --- |
| Python | PEP 8、Google Python Style Guide | 不为满足格式而破坏兼容；依据实际运行版本核对语法和 API |
| Go | Google Go、Uber Go Style Guide | 优先保持 Go 惯用法；不要照搬旧工具推荐 |
| Java | Google Java、阿里 Java 开发手册 | 依据项目 Java 版本和框架选用条款 |
| JavaScript / TypeScript / React / Node.js | 阿里前端规约；Airbnb 可作另一选项 | 不混用整套风格；核对框架和 lint 配置兼容性 |
| C / C++ | 已有项目规范；Google C++ 作补充 | 异常、内存和 ABI 策略以项目实际契约为准 |
| C# / .NET | 项目 `.editorconfig`；微软 C# 约定 | 微软示例、运行时和编译器项目的规则并不完全相同 |
| REST API | Microsoft Azure REST API Guidelines | 参考契约设计原则，不强制复制 Azure 专用路径、版本参数或内部审批流程 |

以上来源链接见 [sources.md](sources.md)。只在当前任务需要且本地证据不够时核对官方文档，不自动引入新格式化工具。

## 跨语言质量要求

- 名称传达用途、单位和业务含义；避免模糊的 `data`、`temp`、`util` 成为主要接口语义。
- 函数、模块和文件有清晰职责；复杂分支优先降低嵌套、明确条件，文件长度按下方规则评估，行数不能替代职责与可维护性判断。
- 公共接口有明确类型/结构、错误语义和副作用；无需在每个内部函数上堆叠重复文档。
- 数据与指令分离：结构化数据用解析器，查询值用参数绑定，系统命令用明确程序和参数数组。
- 维护模块边界和依赖方向；新增抽象、缓存、并发和依赖分别说明收益以及维护成本。
- 资源按明确生命周期释放；异步任务可取消、可等待；错误保留必要上下文，不重复处理或泄漏秘密。
- 不忽略返回值、取消信号或 Promise 错误；不把空集合/默认值当作所有异常的通用解决方案。
- 对外文档描述契约；内部注释说明不明显的理由。代码变化时同步维护相关说明。

## 模块清晰与文件长度

- 每个手写源文件必须保持单一、清晰的职责，围绕同一内聚目标组织；不得将多个独立模块或无关业务职责堆在一个文件中。职责已混杂时，即使文件未达到长度阈值，也须评估合理拆分。
- 优先遵守项目明确的文件长度或拆分约定；没有约定时，以 **1000 行作为拆分评估阈值**。本次新增或修改的手写源文件超过 1000 行时，必须评估拆分，不得无说明持续堆叠代码。它不是硬性上限；达到 1000 行但未超过时，不因行数单独触发评估。
- 默认统计文件全部物理行（含空行、注释），项目另有统计方式时沿用。不得通过压缩语句、删除有意义的注释或改变格式来规避评估；没有实际计数时，不声称已检查长度。
- 按业务职责、内聚性、接口和依赖关系拆分，不按固定行数机械切割；本次授权范围内有合理边界且能安全拆分时应拆分，保持行为、错误、副作用和依赖方向。不得制造碎片文件、循环依赖或仅用于转发的无意义层次。
- 确需保留超阈值文件时，在当前任务、已有维护记录或交付说明中记录路径、实际行数、职责判断、保留原因及后续建议；不强制另建文档或新增审批。拆分若超出授权、改变公共契约/模块边界或涉及高风险，先按适用流程澄清或确认，不因长度要求越权。
- 生成代码、锁文件和第三方/供应商代码不适用默认阈值，不直接修改生成物来满足长度要求；豁免依据须可核验，手写代码不能仅凭名称自称生成代码。只评估本次涉及的文件，不为清理既有超长文件扩展成无关全项目重构；只读评审只报告，纯文字/格式维护不自动授权结构拆分。

## 自动检查

- 使用仓库现有的 format、lint、typecheck、编译和测试命令，核对命令是否会修改文件或产生外部副作用。
- 格式化只覆盖本次范围，除非用户明确要求全仓库统一。
- 必须解释新增的规则豁免，尽量限定到具体代码；不要为消除报错禁用整个规则或降低全局检查强度。
- 命名、行宽、覆盖率、依赖数量等不是独立的质量保证；不要把某个大厂的数字自动变成当前项目门槛。
