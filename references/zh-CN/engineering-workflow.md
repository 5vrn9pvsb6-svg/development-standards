# 工程流程

中文规则源 | [English](../en/engineering-workflow.md) | 配对修订：`2026-10-05.9`

以微软 ISE Playbook 的 Ready/Done、设计评审和工程检查清单为流程参考。“正式开发先确认需求文档，新项目还须确认技术栈，再确认模块与架构文档，最后编码”是用户指定的流程门槛；符合条件的低风险局部修复采用轻量通道。两者不是宣称所有大厂采用同一审批制度。出处见 [sources.md](sources.md)。

## 先选择任务流程

沿用 [核心规范](standards.md) 的任务模式。后面的需求、架构文档门槛和确认记录针对正式开发；只读、文档工作、轻量维护和合格局部修复不因缺少两份已确认产品文档被误阻塞。低风险行为保持重构的资格及前后验证统一见核心规范，不套用缺陷修复的旧实现失败条件。

### 低风险局部修复

资格、简述、澄清与升级规则统一见 [核心规范](standards.md) 的局部修复通道，验证与记录见 [验证与交付](verification-and-delivery.md)。合格修复不套用下方正式开发的两份文档门槛；涉及多个既有模块也按实际影响判断，不按模块数量自动升级，不豁免高风险、安全或旧 Agent 证据要求。

## 阶段一：讨论需求并形成文档

先读现有文档、实际实现和相关约束，区分已确认事实、模型假设和用户尚未决定的事项。按影响集中提问，先解决目标与边界，再解决业务规则和验收；不要让用户一次回答与当前项目无关的长问卷。

讨论至少覆盖：

- 目标用户、要解决的问题、典型操作流程和期望结果。
- 本次包含什么、不包含什么；哪些既有行为必须保持。
- 功能规则、输入输出、边界和异常；涉及的权限、隐私和数据归属。
- 依赖、兼容及约束；适用的性能、容量、可用性目标，不能编造指标。
- 新项目收集影响技术选型的运行平台、部署条件、预算、维护人员能力、现有系统及用户已指定的技术；用户不了解技术时询问期望与限制，不让其先选框架。
- 存在客户端 Agent 与 Server 通信时，明确低版本兼容范围、依据和必须保持的协议/核心流程；范围不清时询问，不自行淘汰旧版本。
- 每项需求可观察、可验证的验收条件；未决问题是否影响设计或实现。

使用仓库既有格式；没有时根据文档目标语言参考 [中文需求模板](../../assets/zh-CN/requirements-template.md) 或 [英文需求模板](../../assets/en/requirements-template.md)，落盘到 `docs/requirements.md`。大型项目可按功能拆分，但要有明确入口。为需求使用稳定编号，例如 `REQ-001`，便于后续映射到模块和验收；不强制使用同一编号格式。

文档不能只是聊天转录或功能名称列表。记录可执行的规则与验收、非目标、未决项及讨论结论；缺失信息明确标为待确认，不能把模型推断写成业务事实。

落盘后向用户提供文件路径、关键结论和影响下一阶段的待决项，请求确认。仅获得针对本次范围和当前内容的明确确认后，记录确认来源及适用范围，进入架构讨论。不能只创建文件就视为需求门槛通过，不能用用户最初的开发请求冒充对后续草案的确认。

## 阶段二：讨论模块与架构并形成文档

### 新项目先讨论并确认技术栈

基于已确认需求筛选方案，不为尚未确定的业务功能提前锁定技术。先沿用用户明确指定的技术和项目约束；发现冲突时解释影响并请用户决定，不静默替换。已有项目复用适用的已确认技术栈，不把普通缺陷修复变成重新选型。

面向非技术用户，通常提供 2–3 个实际可行的方案并标明推荐项；只有一个符合约束时解释原因，用户已指定时不要求重复选择。比较方案组合而不是罗列工具名，按适用性说明语言/运行时、客户端或前端、服务端、存储、测试/构建和部署方式；无需某组件时注明不需要，不为填表引入数据库、微服务或云服务。

| 方案及推荐理由 | 通俗说明与适用场景 | 主要技术组成 | 交付/运行成本与维护负担 | 扩展能力、限制及风险 |
| --- | --- | --- | --- | --- |

先讲用户可感知的差异，再补具体技术名称；不要让用户只凭陌生缩写选择。成本、工期和性能描述区分依据、估算与未知，不编造数字或保证。需要比较具体版本、维护状态、许可证或服务价格时核对当前官方来源，未核实的关键项明确记录，不用过时记忆定案。

请用户选择方案或确认推荐方案；确认也可随包含清晰选型的架构草案一并取得，但未定案时只写设计草案，不写成已选用。用户让模型推荐或代为选择时，提出结论和理由供其确认，不把“我不懂技术”或请求推荐本身视为对具体选型的批准。

把选型结论、关键组件及兼容的版本/版本范围、选择理由、确认来源与适用范围记录到架构文档。仅用户明确指定部分技术时，沿用该部分；只追问仍影响正确性、成本、部署或维护的选择，不要求用户逐一批准每个传递依赖。技术栈确认不会自动批准整个设计，也不会授权创建收费资源、部署或其他外部操作。

技术栈与本次实施范围的完整设计门槛未通过前，不初始化正式工程、安装项目依赖或生成正式代码/测试。安全只读调研和文档工作可以继续；需要实验验证方案时按后文的探索实验规则单独授权、隔离运行。选型发生实质变化，如更换主要语言/框架、存储或部署模式，先解释兼容、成本和维护影响，更新设计并重新确认；同一方案内不改变这些约束的常规兼容补丁不自动使确认失效。

### 模块与架构设计

从已确认的业务场景划分职责，先检查现有模块和框架的归属；优先复用已有边界，不能默认引入微服务或额外分层。与用户讨论关键取舍，解释模块为什么这样划分、如何协作，以及主要失败路径。

使用仓库既有格式；没有时根据文档目标语言参考 [中文架构模板](../../assets/zh-CN/architecture-template.md) 或 [英文架构模板](../../assets/en/architecture-template.md)，落盘到 `docs/architecture.md`。内容深度按规模和风险调整，但至少交代：

| 项目 | 必须交代的内容 |
| --- | --- |
| 系统边界 | 系统内部、外部参与者和依赖；关键场景的调用或数据流 |
| 技术栈 | 主要语言/框架、存储、构建/测试与部署方式及适用版本；新项目的方案取舍、确认来源与范围 |
| 模块职责 | 每个模块负责什么、不负责什么；代码归属路径、主要接口及允许的依赖方向 |
| 契约与数据 | 输入输出、错误和副作用；数据由谁拥有、谁能读写，适用的事务/一致性和兼容性变化 |
| 失败与资源 | 超时、取消、重试/幂等、并发竞争和资源释放，按适用性说明 |
| 非功能与安全 | 真正适用的性能、可观测性、权限、隐私和恢复目标 |
| 取舍与验证 | 重要备选方案、选择理由、未决项；如何检验关键假设 |
| 需求映射 | 本次每项需求由哪些模块实现，在哪里验证验收条件 |

用模块表展示“职责、不负责的事项、路径、接口、依赖”，不能只给目录树或组件名称。关键场景说明从入口到业务处理、存储/外部调用和错误返回的流向；复杂模块和复杂流程必须按下方图示规则配图，不用图代替接口契约。尚不存在的代码路径标为规划，不写成已实现。

确保业务规则有明确归属，不把权限判断交给客户端，不让多个模块复制同一规则，不绕过模块接口直接修改其他模块内部数据。层数、模块数和服务数不是质量指标。

### 界面设计先提供三套视图效果方案

涉及新界面或实质重设计时，基于已确认需求，在本阶段输出 3 套方案供用户选择；纯设计任务在已授权设计范围内执行，不强制进入产品编码。先核对目标用户、核心任务、代表性页面、平台/视口及已有品牌/设计系统；三套都遵守同一业务、安全、可访问性和项目约束，不为凑数改变功能、权限、技术栈或引入无关页面。

- 用方案 A/B/C 标识三套有实质差异的设计，不固定套用某三种风格。采用相同内容、示例数据和目标尺寸，展示同一代表性页面/关键任务；差异可体现在导航/布局、信息密度、排版与视觉层级、控件/操作组织，不能只换颜色、名称或把不可行方案当陪衬。
- 每套必须交付浏览器可查看的 HTML 视觉原型/示意页面，默认用静态 HTML/CSS，JS 非必需。重点打磨美观、布局比例、配色、字体、间距、组件一致性、视觉层级及内容组织，贴合产品场景和既有设计系统；不能只给文字、无样式线框、空占位或换色稿。只制作决定视觉方向所需的代表性页面/状态，不先做三个完整产品。提供每套入口并说明适用性、差异和重要代价，推荐不代替选择；图片可以辅助，但不能只交图片而不提供 HTML 页面。
- 不要求按钮、导航、表单、筛选、弹窗或业务流程完整可操作，也不要求校验、状态管理、API 或登录。帮助视觉对比的低成本轻量交互可按需添加；仅当用户明确要求交互演示时实现指定范围并检查，不自动补全所有功能。静态控件不构成视觉方案缺陷，但不能宣称未实现的功能已可用。
- 原型是隔离设计工件，使用合成示例数据，在设计记录/交付中说明仅视觉展示及适用的未实现范围，不冒充业务完成。已授权界面设计可以制作并本地预览 HTML/CSS，必要时加 JS，不初始化正式工程、安装正式项目依赖、连接真实服务/凭证/敏感数据。新工具、外部写入和真实操作仍须适用授权；仅禁止脚本/交互执行时使用无 JS 静态页面，禁止浏览器预览时不越权，报告渲染未验证。
- 默认可保存到 `docs/ui/option-a/index.html`、`option-b/index.html`、`option-c/index.html`，仓库已有位置优先；资源相对引用且随原型保存。优先可直接打开的轻量 HTML 页面并提供实际文件链接；确需本地服务时使用可用工具和空闲端口，仅本地访问，给出实际可访问 URL 及运行方式，不擅自上传/发布。快速检查三套入口、资源和目标代表性视口的视觉显示、可读性及溢出/遮挡；默认不逐控件做交互或端到端测试，报告真实渲染结果与未运行项。详见 [验证与交付](verification-and-delivery.md)。
- 在已有设计记录或架构文档中保存三套预览引用、方案版本/范围、比较结论及用户真实选择。无既有位置时可在 `docs/architecture.md` 关联 `docs/ui/` 资源，不另造固定审批台账。用户可单独选择或随明确包含界面方案的架构一起确认；推荐、沉默、最初开发请求或仅批准技术栈不算选择。选择界面不自动批准整个架构，也不授权未批准的产品代码。
- 用户要求组合/调整时，展示修订后的效果并确认受影响内容再实现；复用适用于当前范围的有效既有选择，落实同一方案、保持既定设计的修复/文字修正不重新选型。发现实际需要重设计则按本次范围重新提供三套，用户本次明确要求三套时不以旧选择省略；不使无关页面或确认失效。

缺少三套 HTML 视觉原型或尚未获得选择时，保留对应界面为设计待完善/待选择，不实施尚未确定的正式界面；不因未实现可选交互而拒绝合格的静态 HTML 方案，也不阻塞已确认且独立的非界面范围。正式开发仍须通过需求、技术栈和本次完整架构门槛；无界面的产品不生成空方案，也不为本要求添加界面。

### 复杂模块与流程的必需图示

在本次架构范围内判断复杂度：模块内部存在多层职责或子模块协作、交叉依赖、多方外部交互，或流程存在多分支、异步/并发、重试/补偿、状态转换等，使结构关系或执行路径难以用简短线性描述表达时，必须配图。不仅按模块数量、代码行数或文件数量判定，也不能因为只有一个模块就忽略复杂内部流程。

- 复杂模块必须提供架构图，展示相关内部组成、模块边界、关键外部依赖及调用/依赖或数据流方向；边标明含义，节点与模块表一致，不能只摆组件名称。
- 复杂流程必须提供流程图，展示入口、关键步骤及负责模块、判断条件与各分支、结束/结果和关键失败路径；按实际流程表达并发汇合、重试条件/上限或补偿，不编造不存在的机制。多方时序或状态变化可另补时序图/状态图，不代替必需流程图。
- 简单模块及清晰线性流程可用文字/表格，图可选；不为满足规则增加层、服务、节点或全项目图。只读工作不授权新增图文件，合格轻量修复/重构不追补历史架构图；变化已触发正式架构流程时再按本次范围执行。
- 图在提交架构确认前随文档落盘，可内嵌或相对链接到图文件。沿用仓库支持的格式；无约定时优先内嵌可编辑 Mermaid，不要求安装新绘图工具或另造审批台账。检查语法、链接、箭头含义和可读性；有可用渲染环境时检查实际显示，未渲染的部分如实标注，不声称已完成渲染验证。
- 区分现有、规划和待决内容；图与模块表、接口契约、失败处理一致。设计变化同步图及文字，不能只更新一方；补充准确图示或纯布局修正不自动使原确认失效，实质改变设计仍走受影响确认流程。

缺少本次复杂模块/流程必需图示、图只有占位框或与设计矛盾时，对应范围仍是未完成草案，补齐后再作为完整架构提交确认。图与文字属于同一次架构确认，不新增独立图示审批；无关范围不因此阻塞。

架构阶段讨论存储选型、模块数据归属和关键数据契约，不强制提前输出详细数据库设计文档，也不把它作为架构确认附件。数据库设计输出放在下方阶段三的编码开工检查；已有数据库设计可作为参考，不因此要求重新生成。

提交架构文档及关键取舍供用户确认。本次模块/架构设计被确认且需求映射无关键缺口后，才进入实现；用户只确认了需求不等于确认架构。若架构讨论发现必须改变业务需求，回到阶段一更新并确认受影响需求。

## 文档状态与进入实现的条件

正式开发所需的两份文档分别标明当前状态、适用范围/版本、未决项和确认记录。状态可以是草案、待确认、已确认或因变化需重新确认；确认记录必须来自用户的真实反馈，不能虚构审批人、日期或意见。

### 最小确认记录

复用项目既有格式，但两类文档都必须能定位以下信息：

| 字段 | 要求 |
| --- | --- |
| 文档标识与版本 | 文件路径或稳定标识，以及当前内容版本；确认状态和实现证据可另记，不能用它们冒充内容版本 |
| 适用范围 | 本次功能/需求编号、重要非目标；部分确认不能扩展为整份文档批准 |
| 当前状态 | 草案、待确认、已确认或需重新确认，按真实事实选择 |
| 确认来源 | 当前对话中明确的用户反馈，或项目认可且可核验的审批记录；记录对应内容版本，不编造消息 ID 或审批人 |
| 未决项 | 问题、影响、是否阻塞本次范围；没有则明确无阻塞项 |
| 重新确认触发条件 | 需求/验收、权限/数据规则、技术栈、公共契约、模块职责/依赖等实质变化 |

架构文档还记录它依赖的需求文档版本和需求范围。重新进入任务时核对当前内容与确认记录是否对应；仅凭文件自称“已确认”不通过门槛。旧来源无法核验时说明缺口，请用户对当前版本补充确认，不擅自伪造历史；用户当前明确确认适用版本时，不再要求找回原对话。

需求或验收实质改变时，相关需求确认和依赖该内容的架构确认失效；技术栈/架构/契约/模块边界实质改变时，其设计确认失效。标记受影响版本和范围，停止对应实现，更新文档后重新确认。拼写、格式、确认元数据补充及不改变设计的实现证据更新不自动使确认失效；依据实际语义判断，不能借“文档修改”隐瞒业务变化。

版本号或可选内容指纹只用于识别内容，不是用户批准的证明。有效且可核验的既有确认直接复用，不把每次运行变成重复审批。

数据库设计文档不是本节的第三道确认门槛，在阶段三输出和保存。已确认架构范围内的数据库实现细化不自动使确认失效，也不能把尚未由用户确认的细节标为“已确认”；影响已确认需求、技术栈、公共契约、模块边界或权限/数据规则时，仍按本节更新并确认受影响内容。

仅正式开发进入实现前检查：本次范围的需求及完整设计已确认，新项目技术栈已有明确、可核验的确认，必要依赖和阻塞本次实现的问题已解决，每项本次需求有模块归属与验收方式。针对未来迭代的未决项可保留为明确非本次范围，不假装全部已解决。

例如仅 REQ-001 的需求与完整设计获确认，且必要共享依赖均已确认，可实现 REQ-001；独立的 REQ-002 待决不阻塞它，但不得实现 REQ-002、把整份文档标为全部已确认或扩大确认范围。若 REQ-001 依赖尚未决定的共同契约，则该依赖仍阻塞 REQ-001。按范围记录混合状态，复用原确认，不另造审批台账。

已有已确认文档时核对当前范围是否覆盖，内容仍然适用则复用。符合原验收且不改变接口/模块边界的修复不重做架构；正式开发无基线时只补受影响范围。其他模式的豁免见 [核心规范](standards.md)。Issue、聊天或 ADR 可承载局部修复的目标、依据和结果，但不代替正式开发所需的两类项目文档。

正式开发未获确认时停留在对应阶段，但允许提问、讨论、撰写或修订相关文档、记录真实确认，以及代码阅读和安全的只读检查。禁止正式实现、测试实现和基础设施变更。上述已授权的界面 HTML 设计原型按本阶段规则制作与本地预览，不重复索要同一授权；其他探索性原型或技术实验先取得针对实验范围的明确授权，隔离运行并记录结果。原型或实验不代替正式设计或批准，只读任务本身不获得编辑文档的权限。

## 阶段三：编码时输出数据库设计

进入获授权的编码阶段时，先判断本次实现是否使用数据库；后续才发现相关依赖时立即补做此检查。正式开发沿用上方需求、技术栈及模块/架构门槛，合格局部修复或重构沿用核心规范的轻量路径。不使用数据库则说明不适用，不生成空文档或为了模板新增存储组件。

使用数据库时，必须先向用户输出本次设计要点并保存独立文档，再编写相关查询、SQL、ORM 或迁移代码，不能只在聊天中描述或完工后补写。默认 `docs/database-design.md`；优先复用仓库已有独立文档、数据字典或设计入口，提供路径、内容版本和本次范围。按文档语言参考 [中文数据库设计模板](../../assets/zh-CN/database-design-template.md) 或 [英文模板](../../assets/en/database-design-template.md)。

- 新建数据库：给出满足当前需求及已选存储方案的设计，区分规划与现有状态，记录关键取舍和待决项。
- 已有数据库：先读本次相关 schema、ORM、迁移和现有设计，核对结构及语义，不凭空重设计。现有文档准确覆盖且不变时，输出路径/版本和相关要点即可；需改变则先更新，缺文档则只补当前相关实体和访问路径，不追补整个数据库历史。材料不一致或关键结构未知时标明依据与缺口，必要时先询问；不自行连接生产库核实。
- 数据库相关查询修复或重构也适用上述输出/保存要求，文档可简短且范围有限；不由此强制补建需求/架构或重复审批。若用户明确禁止文档编辑，先说明保存要求与授权冲突并取得必要授权，不跳过保存或越权写文件。

| 内容 | 按实际范围交代 |
| --- | --- |
| 依据与范围 | 对应需求、架构（已有时）和模块；信息来源、本次包含/不包含、现有与规划状态。 |
| 实体与关系 | 相关表/集合、数据实体、关系与基数；文字或关系图均可，不能只有名称。 |
| 字段与约束 | 业务含义、类型、空值、默认值、标识/主键、唯一性及适用的引用/校验约束。 |
| 索引与访问 | 对应查询/访问路径、索引及取舍；不编造性能指标或数据库能力。 |
| 归属与一致性 | 模块读写入口、权限、敏感数据与生命周期，适用的事务和一致性边界。 |
| 变更与验证 | 现状与本次变化、数据/消费者兼容；适用迁移顺序、验证、失败处理及真实可行的恢复策略。 |

按规模和风险调整深度，关系型/非关系型按实际模型填写，不为模板引入不适用的表、外键或事务。文档是编码交付物，不新增独立审批或默认暂停等待数据库文档批准。已确认范围内的实现细化可在记录取舍后继续；若实质改变已确认需求、选型、公共契约、模块边界或权限/数据规则，先更新受影响文档并重新确认。迁移、破坏性操作和真实数据访问须有适用授权及兼容/恢复决策，不能以设计落盘代替。

数据库文档解释设计，SQL、ORM 和迁移脚本提供实现，三者需要一致；后续设计变化先同步文档，存在架构链接时同步其版本/范围。只补链接、事实或不改变已确认契约的实现细节不自动重批，也不伪造批准。只读诊断、评审、计划及纯文字/格式维护不触发保存要求。

## 编码阶段的产品版本递增

本规则适用于所有获授权的项目代码变更，包括 Bug 修复及轻量重构，不以是否新增功能或是否发布为条件；适用范围和计数单位见 [核心规范](standards.md)。版本号更新本身及同一次变更内的修正不递归触发再次升版。

- 修改前核对本次受影响产品/组件的当前版本、权威入口和递增规则，例如项目已有的 `VERSION`、包清单或构建配置。遵循项目规定的递增级别，不把“升一个版本”理解为每次升主版本；多组件项目按既有统一/独立版本策略处理，不顺带升级未受影响的 Agent 或其他产品。
- 一次完整变更可涉及多个文件和验证修正，交付前必须在真实入口完成递增，不能仅口头宣布、改文档编号或依赖版本。续接未交付工作时核对这次升版的基线和记录，正确完成则复用；已交付后的新修改需要再次递增。
- 按既有机制同步必要的包/构建/显示版本、锁文件及已有变更记录；只更新实际要求一致的项，不全仓替换所有相同数字、不改变协议或迁移编号。优先复用项目版本工具，结构化文件用对应解析器或已有工具；命令附带提交、标签、发布等副作用时不直接执行未经授权的操作。
- 没有版本入口、初始版本或明确规则，或者仓库仅在发布时升版而与本要求冲突时，先提出最小方案并请用户确认受影响决策，不自行猜测基线或改造发布流程。新项目首次实现记录经确认的初始产品版本，其后每次代码变更递增；版本文件编辑被明确禁止时说明授权冲突，不越权或宣称已完成。
- 在已有任务/修复/变更记录和最终报告中记录旧版本 -> 新版本、版本入口、必要同步项及本次变化摘要；不强制另建版本台账。检查递增符合规则、相关配置可解析及实际可检查的显示/构建版本一致，未运行项如实报告；证据细则见 [验证与交付](verification-and-delivery.md)。

纯文档和只读工作不升产品版本；代码文件中的注释/格式修改仍属代码变更。升版不新增需求/架构审批阶段，不授予提交、标签、合并或发布权限，也不能作为破坏旧 Agent 兼容的理由。

## 任务拆分与变更控制

- 正式开发在两道文档门槛通过后按需求与模块拆分任务；局部修复按已明确目标、范围和验证方式实施。每一步应有可检查结果，合入后保持系统可构建、可测试。
- 大规模重构先保护现有行为，再拆成可审阅变更；不要把“重构”当作静默改变行为的理由。
- 发现需求、技术栈或模块边界实质变化时说明验收、设计、测试和工作量的影响；先更新受影响文档并取得确认，再继续相关实现。不能在编码后追认关键决定。
- 实现阶段不擅自执行部署、生产迁移或外部写入；设计方案本身不授予执行权限。

## 接口和数据变更

- 公共接口记录新增、修改或废弃的契约，检查所有已知消费者；不得静默改变默认值、错误语义或字段含义。
- 修改重试行为时检查幂等性、重复副作用和重试上限；重试不能代替根因处理。
- 数据迁移交代现有数据兼容、执行顺序、验证和恢复方式。无法回滚时明确前向修复策略，不承诺不存在的回滚能力。
- 本地临时测试与真实数据操作分开；使用脱敏或合成数据，破坏性验证只能在明确授权的隔离环境中进行。

### Server 与 Agent 协议兼容设计

仅适用于有客户端 Agent 通信的产品，遵循 [核心规范](standards.md) 的低版本兼容红线：

- 记录用户/项目规定的 Agent 版本范围和来源，以及旧版本实际请求、响应、接口和流程契约。检查字段的存在性、类型、默认值、单位、枚举、错误语义及序列化行为；不假定旧解析器会忽略新增字段。
- 分析 Server 变更的直接和间接影响，包括认证、配置、数据处理及关键交互流程。按产品适用性列出连接/注册、心跳、任务交互、结果上报等流程，不只检查接口路径未改名。
- 形成新 Server 与低版本 Agent 的兼容矩阵，说明每项契约变化和保持旧行为的方案。可按实际协议采用兼容适配、双协议或能力协商，但不能假设旧 Agent 已支持新协商机制，也不能要求其升级后才能维持既有流程。
- 将矩阵关联到验收场景和测试证据。需求或设计获批、制定 Agent 升级计划，都不能替代兼容验证或使破坏兼容的变更获得合并/发布资格。

## 完成条件

完成与停止条件统一见 [核心规范](standards.md)，实际证据要求见 [验证与交付](verification-and-delivery.md)。沿用开工时的模式，不在交付时重新要求已豁免的文档；文档工作可交付待确认草案，不声称已实施。

人工审批、产品确认、上线观察属于另外的状态。不能因为 AI 已自审或测试通过而声称这些状态也已完成。
