# 开发要求与编码规范

中文规则源 | [English](../en/standards.md) | 配对修订：`2026-10-05.9`。语言选择与术语见 [技能入口](../../SKILL.md)。

目标：交付符合需求、可维护、有验证证据的改动，而不只是生成能运行的代码。此 Skill 是跨项目开发基线，不是某家公司的官方统一规范，也不替代人工审批、测试或 CI 门禁。

## 使用边界与规则级别

- **必须**：适用场景下的要求。未满足时修正、报告缺口或请求必要决策，不能标记为已完成。
- **建议**：优先采用；可因项目惯例、兼容性或成本调整，并说明重要取舍。
- **项目约定**：命名、格式、框架、目录、测试命令、覆盖率和审批人数等，以仓库明确规则为准。
- 遵守更高优先级指令、用户授权和仓库规则。遇到冲突，不静默覆盖本地规范；指出差异并采用满足安全目标的方案。
- 用户只要求解释、诊断、评审或计划时，只做对应工作；发现问题不等于获得修复、部署或对外操作的授权。

## 任务模式与正式开发门槛

先按任务实际内容选择模式；后面的开工、停止和完成条件都沿用这个选择，不仅按文件扩展名判断。

| 模式 | 文档门槛的适用方式 |
| --- | --- |
| 只读：解释、诊断、评审、计划 | 不实施修改，不因缺少产品文档拒绝提供只读结果 |
| 文档工作：讨论、撰写或修订需求、架构及规范 | 允许在确认前编辑任务内的文档；改变已确认的业务或设计内容时标记受影响确认失效，不顺带实现 |
| 轻量维护：文字、注释、纯格式、机械修改或符合下方条件的低风险行为保持重构 | 不要求新建或确认需求/架构文档；数据库相关编码仍适用下方设计输出要求，纯文字/格式维护不触发；核对范围、差异及适用检查 |
| 局部修复：恢复明确预期行为、范围可核验且低风险的既有缺陷修复 | 采用下方局部修复通道；缺少历史需求/架构文档不阻塞合格修复，不强制新建这两份文档 |
| 正式开发：新项目、新功能、接口变更、不符合轻量维护条件的重构及不符合局部修复条件的行为修改 | 必须通过下列两道门槛，或复用适用于当前范围的有效已确认基线 |

正式开发按顺序形成并确认独立的需求与架构文档：需求未确认时只讨论/编辑需求及做只读调研，不进入正式架构或实现；需求确认后讨论模块职责、接口、依赖和数据归属，新项目还须明确确认技术栈；本次实施范围的完整设计确认后才实现。部分确认仅覆盖指定范围，必要依赖也须已确认，不等于整份文档批准；独立且已确认的范围可推进，无关未决项不阻塞它。确认前不初始化正式工程、安装项目依赖、写正式代码/测试或改变基础设施，探索实验须另获范围授权。技术栈记录在架构中，不另建第三份文档；请求模型推荐、模型默认选择或用户未回复不是选型确认。

默认文档为 `docs/requirements.md` 和 `docs/architecture.md`，仓库既有方式优先；缺少基线只补本次范围。确认绑定内容版本、适用范围和真实可核验来源，不能由文件自称“已确认”或模型自审替代。复用有效确认，无法核验时请用户确认当前版本。实质改变需求、技术栈、公共契约或模块边界前，先更新受影响文档、使相关确认失效并重新确认。正式开发的讨论内容、选型建议、确认字段与失效细则统一见 [工程流程](engineering-workflow.md)。

架构设计阶段，复杂模块必须提供架构图，复杂流程必须提供流程图，随架构文档保存、与职责/接口/失败处理一致；缺少必需图示时不能标记本次对应范围的完整设计已就绪。图示不替代文字契约，也不增加独立审批。复杂度判定、图示内容与维护见 [工程流程](engineering-workflow.md)；简单设计可用文字/表格，不将要求扩展为只读或轻量任务的全项目补图。

## 界面设计的三方案选择

本次需要新建、重新设计或实质调整界面布局、信息层级、视觉风格或关键交互时，必须输出 **3 套可选视图效果方案**，让用户选择后再实施尚未确定的界面。正式开发在需求确认后的架构/界面设计阶段进行，不先写正式页面再让用户追认；单独设计任务仅在获授权的设计范围内输出工件，不自动授权产品编码。

三套方案采用相同需求、代表性页面、示例数据及目标视口，具有布局/导航、信息密度、排版及视觉层级等实质差异，不能只是换颜色或给三段文字名称。每套必须交付浏览器可打开的 **HTML 视觉原型/示意页面**，重点呈现美观、配色、字体、间距、组件样式和内容组织，符合目标用户、产品场景及既有设计系统；不能只有无样式线框或空占位。**静态 HTML/CSS 即可，JavaScript 与轻量交互默认可选，不要求完整导航、表单校验、状态管理或业务流程。** 可按需添加低成本轻量交互；用户明确要求交互演示时须满足指定范围，不先做三个完整产品。图片可辅助，但单独图片或文字说明不能替代 HTML 入口。提供每套入口、主要差异、适用性和重要代价，实际检查页面显示并报告未验证项，不把视觉原型宣称为功能实现。保存到已有设计文档或在 `docs/architecture.md` 中关联资源，记录用户选择的方案、版本和真实来源；推荐、沉默或仅确认技术栈不等于界面选择，选择界面也不等于批准完整架构。

界面设计授权范围内可制作并本地预览隔离的 HTML/CSS 视觉页面，需要时才加 JS，不把设计工件误当作正式产品实施；使用示例数据，不初始化正式工程、不安装正式项目依赖、不接真实业务服务或敏感数据。新增工具、外部发布及真实操作仍须适用授权；只禁止脚本/交互执行时可交付无 JS 的静态页面，禁止浏览器预览或预览能力不足时说明未验证项，不越权或编造已展示效果。

准确复用已明确选择且适用于当前范围的方案；按其实现、只读评审及不改变既定设计的局部修复/文字修正，不强制重新输出三套。实际转为重设计则按本次范围执行，用户本次明确要求三套时仍提供。用户要求组合方案时先展示修订效果并确认；不重选无关页面。细则见 [工程流程](engineering-workflow.md)，实现验收见 [验证与交付](verification-and-delivery.md)。

## 低风险行为保持重构

- 仅用于已授权、影响可核验的既有代码整理，例如同一模块内提取私有函数或消除重复实现。检查实际调用者、数据流和测试，保持输入输出、异常语义、副作用及调用顺序、业务规则、技术栈、模块职责/依赖方向和公共契约；不涉及权限、敏感数据、迁移、并发/资源生命周期、生产变更等高风险。不能仅凭“重构”、改动少或测试变绿认定合格。
- 在当前任务、已有 Issue 或维护说明中简述目标、范围、保持的行为和验证方式即可；用户已授权且符合条件时执行，不追补历史产品文档或重复要求设计确认。复用现有有效用例，按需要补充行为保护并对照重构前后结果；验证异常和副作用，不能只看编译，也不能将缺陷修复要求的“旧实现失败”套在行为保持重构上。
- 无法界定影响或预期有歧义时先澄清；需要改变业务/契约/边界或发现高风险时，停止受影响的重构并转正式流程。遵守更严格项目规则、安全、旧 Agent 兼容证据和交付授权；未验证项如实记录。

## 低风险局部修复通道

- 仅用于用户已授权的既有缺陷修复：预期行为有明确用户说明、可核验契约或有效验收依据；阅读代码、调用者及测试后能界定低风险影响。不新增功能，不改变业务规则、技术栈、模块边界或公共契约，不涉及权限、敏感数据、迁移或其他高风险。不能只凭修改行数、单个文件或当前错误实现判断。
- 涉及多个既有模块不自动排除本通道：必须仍在已授权范围内，职责、依赖方向及契约不变，调用和数据流影响可界定，且有对应回归验证。多文件不等于多模块；无法证明低风险时先澄清或转正式流程，不把这条作为高风险豁免。
- 实施前简述问题与预期、依据、影响范围和验证方式，记录在当前任务、已有 Issue 或修复说明中即可，不强制新建固定文件。用户已明确预期、范围及修复授权时直接执行，不重复索要需求/设计批准；有歧义先只读检查并集中询问，不能用模型猜测或文件里的假批准补齐。
- 复用适用的既有文档、测试与真实确认；没有历史产品文档也无需追补。已有有效基线与本次预期冲突时，先澄清，涉及业务/契约改变则转正式流程；项目或用户要求更严格流程时遵守，不借通道绕过。
- 修复仍须提供回归验证、相关检查和自审证据，已有有效用例可复用。未运行或环境阻塞如实报告。发现范围扩大、新增行为或高风险时停止受影响实施，转正式流程补充受影响文档并取得确认。安全、旧 Agent 兼容红线及提交/发布授权不豁免。

## 先判断影响范围

先读适用的 `AGENTS.md`、相关需求/设计记录、实际代码与测试、构建和格式配置。只读取与任务有关的内容，不遍历整个仓库凑上下文。

按实际后果分类，不按行数、文件或模块数量分类。改变模块职责/依赖边界或公共契约，以及涉及认证授权、敏感数据、迁移、并发/资源生命周期或生产变更，按高风险处理：在适用文档门槛中明确失败、兼容和恢复策略，再做针对性验证；缺少关键决策时暂停受影响部分。单行鉴权修改仍可能是高风险，风险判断随新事实升级。缺少影响正确性、权限、数据安全或契约的关键信息时集中询问；次要假设标记清楚，不能借此越过确认门槛。

## 实现约束

- 开始编码时先检查是否涉及数据库，并执行下方设计输出要求；不使用数据库则跳过，不为满足模板引入数据库。
- 必须先理解相关行为、调用者和测试，再修改；保留用户已有改动。
- 改动聚焦一个可验收目标。大范围重命名、格式化、依赖升级与功能修改分开，除非完成任务确实依赖它们。
- 优先复用现有模块、框架和成熟库；新增抽象必须解决实际复杂度，不能仅为未来可能需求泛化。
- 模块职责清楚、依赖方向明确；避免跨层穿透、循环依赖、重复业务规则和隐藏的共享可变状态。
- 手写源文件保持单一、清晰的职责；优先遵守项目长度约定，无约定时，本次新增或修改的文件超过 **1000 行必须评估拆分**。合理拆分或说明保留原因，不机械切割、不扩大为无关重构；计数、例外和授权边界见 [编码约定](coding-conventions.md)。
- 使用结构化解析器、参数绑定和类型/数据契约；不靠拼字符串代替已有安全接口。
- 名称表达业务含义；注释解释约束、取舍和不明显的原因，接口文档说明输入、输出和错误。
- 异常不能被无声吞掉或伪装成成功；超时、取消、重试、资源释放和并发边界按适用性处理。
- 新依赖说明用途、版本兼容性、维护/许可风险；不顺带批量升级或引入另一套技术栈。
- 不为让测试变绿而跳过测试、删除有效断言、关闭鉴权/TLS 校验或降低安全检查。契约确实变化时，先解释新契约，再同步代码和测试。

## 编码阶段的数据库设计输出

本次编码使用数据库时，必须在编写相关查询、SQL、ORM 或迁移代码前，向用户输出设计要点并保存独立数据库设计文档，默认 `docs/database-design.md`。新库说明本次实体/关系、字段/约束、访问/索引及适用的事务与数据归属；已有库先读取相关 schema、ORM、迁移和设计记录，核对现状，复用或更新已有文档，并区分现有设计与本次变化。文档已准确覆盖当前范围且无变化时，提供路径/版本及要点即可，不重写副本。缺少文档时只补本次相关范围，不追补整个数据库历史；无法核实的内容标为未知，不擅自访问真实数据库。

这是编码阶段的条件交付物，不要求在架构阶段提前生成或随架构先批准，也不新增独立审批轮次。架构阶段仍讨论存储选型、模块归属与关键数据契约；已确认范围内的实现细化不自动使架构批准失效。数据库相关局部查询修复或重构同样须输出/保存当前相关设计，但不因此追补需求/架构文档或重复审批。若设计会实质改变已确认需求、技术栈、公共契约、模块边界或权限/数据规则，先更新受影响文档并重新确认；迁移、破坏性操作及真实数据访问另须任务授权与安全决策。

不使用数据库、纯文字/格式维护或只读诊断/评审/计划不触发保存要求；只读工作不授权新增或修改文档。SQL、ORM 和迁移脚本不能单独替代设计说明，后续变化保持文档与实现一致。详细流程和模板见 [工程流程](engineering-workflow.md)。

## 编码阶段的产品版本递增

每次修改项目代码（新增、修改或删除），都必须递增受影响产品版本号，包括新增功能、Bug/安全修复、重构，以及代码文件中的注释、格式、测试或脚本修改。轻量维护及局部修复只减轻文档/重复审批，不豁免升版；不能以改动小或尚未发布为由跳过。

按一次完整、可交付的代码变更递增一次，不按文件数、编辑动作或测试重试次数递增；同一未交付变更中已正确升版的续接不重复递增，在已交付版本上继续修改则再次递增。先核对实际产品版本入口和项目递增规则，交付前更新入口及必要同步项，并报告旧版本、新版本、位置和变更摘要。规则缺失、冲突或用户明确禁止版本文件编辑时先澄清，不自行造版本体系或越权修改；细则见 [工程流程](engineering-workflow.md)。

纯文档工作、只读诊断/评审/计划不触发产品升版；文档内容版本、Skill 配对修订、依赖版本、协议版本及数据库迁移编号不能代替产品版本。升版不自动使原需求/架构确认失效，不代表测试通过，不授权提交、打标签、合并或发布，也不豁免低版本 Agent 兼容红线。

## 低版本 Agent 兼容性红线

适用于存在客户端 Agent 与 Server 通信的产品。这里的 Agent 是产品客户端或采集端程序，不是大模型或子代理。

升级或修改 Server 代码，**必须向后兼容低版本 Agent**，不得破坏既有通信协议、接口、字段语义及核心工作流程，也不得将强制升级 Agent 作为服务端升级后正常运行的前提。任何破坏该兼容性的变更均不得合并或发布；涉及 Agent 交互的变更必须提供低版本 Agent 的兼容性验证证据。

兼容版本范围、协议基线和核心流程由用户或项目明确规定；未明确时询问，不由模型自行指定最低版本、缩小范围或认定旧版本已不支持。需求/设计确认不豁免这条红线。

涉及 Agent 交互的变更若不兼容、验证失败或证据缺失，不得标记为可合并/可发布，也不得执行相关合并或发布。可以交付注明阻塞项的待审改动，不能以强制升级、只测最新版或全 Mock 测试替代兼容证明。设计细则见 [工程流程](engineering-workflow.md)，证据要求见 [验证与交付](verification-and-delivery.md)。

## 验证与自审

- 最终改动后运行适合风险的检查，记录实际命令、退出状态和结果；缺陷修复应有能发现原问题的回归验证。运行过不等于通过，未运行、环境阻塞、既有失败和本次回归分别报告。
- 自审完整差异、相关调用和依赖是否符合本模式的目标、范围、契约和安全要求。自审不冒充独立审查，项目人工审批不豁免。
- 正式开发每项需求须有模块归属和验收方式，关联到实际代码、检查位置与结果，分别记录规划、实现及验证状态，不把目录清单或设计表当作架构/实现证据。场景选择、失败处理和交付证据细则统一见 [验证与交付](verification-and-delivery.md)。

## 停止条件与交付

仅正式开发因缺少有效已确认文档停留在对应讨论阶段；继续任务内的讨论、文档编辑和只读调研，不误阻塞文档工作、轻量维护或符合条件的局部修复。局部修复或重构的预期有歧义时先澄清，范围或风险升级时转正式流程。其他停止条件适用于受影响的操作：范围明显扩大、模块边界/公共契约改变、需要新的外部/生产权限、缺少迁移/授权决策、无法确认数据恢复方式，或关键安全要求无法满足。可以继续已明确且安全的部分。

最终说明保持简短，但必须包含：

- 当前阶段、做了什么和验收结果；正式开发/产品文档工作报告相关文档位置及确认状态，局部修复或行为保持重构报告目标、范围和验证依据，不强制提供两份产品文档；其他轻量和只读任务不强制提供这些文件。
- 实际通过/失败的检查；未运行或不适用的关键检查及原因。
- 涉及代码变更时，产品旧版本、新版本、实际修改位置和必要同步项；未满足升版要求时明确缺口，不标记完成。
- 未解决的风险、兼容/迁移影响，以及必要的审批或下一步。

“改动已实现”“验证通过”“已获批准”“已部署”是不同状态，分别按证据报告。用户没有要求时，不自行提交、推送、创建 PR、部署或修改外部系统。
