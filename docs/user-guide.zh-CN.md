## 1. 快速开始

在任务消息中明确写出 `使用 $development-standards`，再说明你的目标和允许的操作。Codex 支持显式指定技能，也可按任务与描述自动选择；CLI/IDE 扩展可用 `/skills` 或 `$` 选择。界面入口可能随客户端不同，直接在消息中指定技能名不依赖某个固定按钮。参见 [OpenAI 官方技能说明](https://learn.chatgpt.com/docs/build-skills#how-chatgpt-and-codex-use-skills)。

新项目可以这样开始：

```text
使用 $development-standards 帮我开发一个本地待办管理工具。
目标用户是我自己，主要在电脑上使用，暂不做账号登录或云同步。
我不了解技术，请先用中文与我讨论需求，形成需求文档。
需求确认后，请提供可行的技术栈选项、说明推荐理由，再讨论模块与架构。
适用的需求、技术栈和完整设计确认前，不初始化工程或编写正式代码/测试。
本次不授权提交、推送、部署或创建收费资源。
```

你不必先读完所有规范，也不必预先选好框架。先说明要解决的问题和限制，模型应分阶段询问关键问题。

技能是模型行为指引，不是运行时拦截器。显式调用使意图明确，但不保证每次选择或执行都正确；仍须检查文档、代码和验证证据。

## 2. 开始前准备什么

尽量提供已经知道的信息；未知项可以写“待讨论”，不要为填表编造条件。

| 信息 | 你可以怎样说明 |
| --- | --- |
| 目标与使用者 | 谁使用、遇到什么问题、完成什么操作算有用。 |
| 本次范围与非目标 | 这次必须做什么，哪些能力留到以后。 |
| 项目位置与现状 | 新项目或已有项目；工作目录、相关模块、文档或 Issue。 |
| 运行与维护条件 | 电脑/浏览器/手机、能否联网、部署条件、预算、由谁维护。 |
| 已知技术与规范 | 已指定技术、仓库约定、现有测试命令；没有也可说明。 |
| 验收与必须保留的行为 | 示例输入和期望输出、异常表现、已有接口或兼容要求。 |
| 操作授权 | 仅讨论、仅诊断，还是允许修改；是否另含发布或真实数据操作。 |

不要把真实密钥、个人数据或生产数据作为示例直接放入提示词；优先提供脱敏或合成材料。需要外部服务、额外权限或真实环境时，先明确任务范围与安全的访问方式。

确保运行环境能找到完整技能目录，而不只有 `SKILL.md`。本次维护环境的安装位置是 `~/.codex/skills/development-standards`，这是本机实际位置，不代表所有 Codex 版本的通用发现路径。其他环境的本地发现位置以 [官方说明](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills) 和该环境实际配置为准；本手册不要求迁移已有安装。

## 3. 判断任务该走哪条流程

由模型检查相关代码、调用者、数据流和项目规则后判断；不能只按改动行数、文件数或任务名称分类。

| 你要做的事 | 流程 | 你主要需要确认什么 |
| --- | --- | --- |
| 解释、诊断、评审或计划 | 只读 | 目标与范围；不因缺少产品文档拒绝检查，也不擅自编辑。 |
| 撰写或修订需求、设计、规范 | 文档工作 | 文档内容与状态；可交付待确认草案，不顺带实现。 |
| 文字、格式、机械修改或合格行为保持重构 | 轻量维护 | 修改授权、影响范围及验证方式；不追补两份产品文档。 |
| 在低风险范围恢复明确的既有预期行为 | 局部修复 | 预期、依据、范围与修复授权；不重复索要需求/设计批准。 |
| 新项目、新功能、接口变更或不合格的修复/重构 | 正式开发 | 先确认需求，再确认本次范围完整设计；新项目另须明确选型。 |

轻量通道减轻的是文档和重复审批，不减免验证、安全或兼容要求。权限、敏感数据、迁移、并发/资源生命周期、生产变更等高风险不能因“只改一行”或“只是重构”而豁免。

发现扩大范围或高风险时，模型应停住受影响部分、解释原因并转入适用流程；已明确且安全的独立部分可以继续。用户或项目要求更严格流程时，不能用本手册绕过。

## 4. 新项目从讨论到交付

```text
需求讨论 -> 需求文档 -> 用户确认
-> 技术栈与模块架构讨论 -> 架构文档 -> 用户确认
-> 实现已确认范围 -> 验证 -> 交付
```

### 4.1 讨论并确认需求

模型先问清目标、流程、范围、业务规则、输入输出、异常、约束和验收条件，形成或更新默认的 `docs/requirements.md`。仓库已有文档位置和格式时优先沿用。

你应重点检查：

- 场景是否符合实际，有没有被模型添加你没要求的功能。
- 验收是否能观察和验证，而不是只写“正常运行”。
- 未知信息是否标为待决；本次包含和不包含的内容是否清楚。
- 必须保留的行为、权限、数据与兼容要求是否遗漏。

需要修改时先提出修改意见。认可当前内容后，可以这样确认：

```text
我确认 docs/requirements.md 的 v1，范围为 REQ-001 的本地待办创建。
REQ-002 的搜索暂不确认，也不纳入本次实现。
请基于这份已确认需求进入技术栈和架构讨论，暂不编写正式代码。
```

这是一种清晰表达方式，不是必须背诵的固定口令。关键是双方能定位被确认的内容版本和范围。需求未确认时，模型可以继续讨论、修订需求和只读调研，不应进入正式架构或实现。

### 4.2 选择技术栈

你不了解技术时，主要表达使用和维护条件，由模型把方案翻译成可理解的取舍：

```text
我希望单人使用、容易安装、数据保存在本机，后续维护尽量简单。
请比较实际可行的方案，标出推荐项。
先说明部署、运行成本、维护负担和限制，再给具体技术名称。
估算或尚未核实的价格、版本与维护状态请明确标注。
```

通常比较 2–3 个真正可行的组合，不要求你逐个选择陌生依赖；你已指定的技术应沿用，只有一个合理方案时也不用凑选项。模型推荐不等于你已批准。

技术栈记录在架构文档中，不必创建第三份选型文档。你可单独确认推荐方案，或与明确写出该方案的完整架构一起确认。单独确认技术栈不等于整个设计已获批准，也不授权购买服务或部署。

### 4.3 检查模块与架构

默认文档为 `docs/architecture.md`，它应关联已确认的需求版本。非技术用户不必审查每行代码，但应能理解每个模块做什么、如何协作、失败时会怎样。

| 检查点 | 判断是否清楚的问题 |
| --- | --- |
| 模块职责 | 谁处理界面、业务规则、存储？分别不负责什么？ |
| 接口与数据 | 模块如何传递输入、结果和错误？谁拥有、允许读写哪些数据？ |
| 关键流程 | 从用户操作到处理、保存和返回结果，顺序是否完整？ |
| 复杂模块与流程图示 | 复杂模块是否有架构图，复杂流程是否有流程图？图中的边界、依赖、分支及失败路径是否与文字一致？ |
| 必要依赖 | 本次能力依赖的共同规则或组件，是否已明确并获确认？ |
| 安全与失败 | 真正适用的权限、失败处理、资源清理和恢复方式是否交代？ |
| 验收映射 | 每项本次需求由谁实现，怎样验证？规划是否被误写为已实现？ |

目录树或框架名称清单不能代替模块设计。合理的小项目可以很简单，不要求为了规范增加微服务、数据库或多余层次。

涉及新界面或实质重设计时，模型必须先交付 **3 套 HTML 视觉原型/示意页面**，供你在浏览器中查看后选择。三套使用相同需求、代表性页面、示例数据和视口，比较布局、信息密度、视觉层级与重要代价，重点看美观、配色、字体、间距、组件样式及内容组织是否适合产品。**静态 HTML/CSS 页面即可，不要求完整可交互；JS、按钮响应、表单校验及业务流程默认不必实现。** 如需演示具体交互可另明确范围，不把方案阶段做成三个完整产品。不能只交文字、图片、空线框或换色稿。提供实际文件链接，必要时提供本地预览 URL，说明仅视觉展示/未实现范围和真实渲染检查结果，不接真实业务服务。你可选一套或要求组合修改；组合后查看修订效果并确认。模型将入口、方案版本/范围和真实选择保存在设计文档，选择可随架构一并确认，但不等于批准整个架构、授权产品编码或产品功能已完成。

```text
请先提供 A/B/C 三套浏览器可打开的 HTML 视觉示意页面，采用相同代表性页面和示例数据。
重点打磨美观、布局、配色、排版、间距与视觉层级，静态 HTML/CSS 即可，不必完整交互。
说明视觉差异、推荐理由、实际渲染检查结果及未实现范围，给我各方案入口。
我查看并选择后再按已确认范围实施，原型不接真实服务，也不冒充已完成产品。
```

已有明确、有效且适用的选择可复用，按既定方案实现或仅修复其 Bug/文字不重新选型；实际重设计或本次明确要求三套时仍提供。只读评审、无界面项目不因此新增设计文件或界面；预览工具不足时应说明缺口，不声称已展示效果。细则见 [工程流程](../references/zh-CN/engineering-workflow.md)。

复杂模块（如多层职责、交叉依赖、多方外部交互）必须用架构图说明组成、边界和关系；复杂流程（如多分支、异步/并发、重试/补偿或状态转换）必须用流程图说明步骤、条件、结果和关键失败路径。图随架构文档保存，项目格式优先，无约定时可内嵌可编辑 Mermaid；时序图/状态图可以补充，但不替代必需流程图。提交完整架构确认前补齐，不能用占位图或聊天中的口头描述替代，不新增一轮图示审批。简单清晰设计可用文字/表格，只读和轻量任务不要求补画全项目图。

架构阶段仍讨论存储选型、数据归属和关键契约，但不强制把数据库详细设计作为待批准附件。数据库设计输出放在下一节的编码开工检查。

确认示例：

```text
我确认 docs/architecture.md 的 A1，依据需求 v1 的 REQ-001。
确认其中明确列出的方案 A 技术栈、本次范围的完整模块设计、数据契约和必要共享依赖。
REQ-002 仍待决，不实施。请实现并验证 REQ-001。
本次允许工作区内的实现与适用检查，不授权提交、推送或部署。
```

这里的“方案 A”须对应你实际读过的明确方案，不能引用尚未定义的名称。适用门槛通过前，不初始化正式工程、安装项目依赖或编写正式代码/测试。若确需验证技术可行性的实验，应另行明确授权实验范围并隔离运行；实验结果不是正式设计批准。

### 4.4 实现、验证与交付

模型只实施已确认范围，复用项目编码约定、框架和成熟库，应用适用的腾讯安全基线。实现中发现需求、选型、公共契约或模块边界须实质改变时，先更新受影响文档并重新确认，不先改完再追认。

编码时每个手写源文件必须保持单一、清晰的职责，不能混放多个独立模块。项目文件长度约定优先；没有约定时，本次新增/修改文件超过 **1000 行必须评估拆分**，默认统计全部物理行（含空行、注释）。1000 行是评估阈值，不是硬性上限；未超阈值也不能忽视职责混杂。按职责和依赖合理拆分，不能机械切割、压缩代码或删除有意义的注释来凑行数。

确需保留时，模型应说明路径、实际行数、职责判断、原因和后续建议，不强制另建文档或审批。生成代码、锁文件和第三方代码可凭可核验依据豁免默认阈值；不为此重构无关旧文件，拆分超出授权或改变契约/模块边界时先按适用流程确认。只读评审只报告，纯文字/格式维护不自动授权拆分。细则见 [编码约定](../references/zh-CN/coding-conventions.md)。

开始编码时，模型必须检查本次是否使用数据库；涉及时先输出设计要点，并在数据库相关查询、SQL、ORM 或迁移代码前保存独立设计文档，默认 `docs/database-design.md`。不使用数据库则跳过，不创建空文档或为了模板增加数据库。可参考 [数据库设计模板](../assets/zh-CN/database-design-template.md)，记录相关实体/关系、字段/约束、访问/索引、归属及适用的事务、兼容迁移和验证。

新库输出拟采用设计；已有库先核对相关 schema、ORM、迁移和文档，说明现状与本次变化。文档准确覆盖且不变时，模型给出路径/版本及要点即可；需变更则更新，缺文档则只补本次相关范围，不重写全部历史。SQL、ORM 或迁移文件不能单独替代说明，也不授权模型连接生产数据库。

它是编码交付物，不要求架构阶段提前生成或批准，不另加数据库审批。已确认范围内的实现细化可继续；影响已确认需求、技术栈、公共契约、模块边界或权限/数据规则时仍先确认受影响内容，真实迁移和破坏性操作仍需单独任务授权。数据库查询修复或重构也输出当前相关设计，不由此补建需求/架构；若明确禁止文档编辑，应先解决保存要求与授权的冲突。只读诊断/评审/计划和纯文字/格式维护不触发保存。

每次完整代码变更（包括 Bug 修复、重构及代码注释/格式、测试/脚本修改）都要递增受影响产品版本，轻量通道也适用。一次变更涉及多个文件或验证修正只升一次，已交付后的新修改再升；先核对项目真实版本入口和递增规则，交付前完成必要同步。新项目首次实现使用与你确认的初始版本；已有项目没有版本规则或禁止改版本文件时，模型应先说明并与你确认，不随意造版本号。纯文档和只读任务不升产品版本，升版不授权提交、标签、合并或发布，也不能代替旧 Agent 兼容验证。细则见 [工程流程](../references/zh-CN/engineering-workflow.md)。

交付时应把需求关联到实际模块、代码位置和检查结果，而不只是宣布“代码完成”。你可要求：

```text
请按本次已确认需求汇报实际实现位置和验收结果。
涉及超阈值手写源文件时，说明实际行数、拆分结果或保留理由。
涉及代码修改时，报告产品旧版本 -> 新版本、实际版本入口及必要同步项。
列出实际运行的命令、通过/失败情况、未运行的关键检查及原因。
区分已实现、已验证、已确认和已部署；自审不要写成独立审查。
```

## 5. 已有项目怎么使用

### 5.1 只诊断、不修改

```text
使用 $development-standards 诊断导出失败的原因。
只读检查相关代码、调用者、配置和测试，给出依据及修复建议。
不修改代码、测试、文档或部署配置。
```

“发现问题”不自动授权修复。诊断后决定实施，再明确提出修复请求。

### 5.2 授权局部修复

```text
使用 $development-standards 修复标签展示问题。
预期只去除显示文本两端的 ASCII 空格，保留内部空格、大小写及其他空白。
本次授权局部修复和相关回归测试，不新增原文查看功能或改变公共契约。
先核对是否低风险，再简述依据、影响范围和验证方式。
若合格，不追补历史需求/架构文档；有歧义或范围扩大先说明并询问。
```

合格修复可以复用已有测试；缺陷回归应能发现旧问题，安全可行时运行旧实现失败、修复后通过的验证。无法回放时应说明限制，不伪造结果。多个既有模块受影响不自动排除轻量修复，仍须证明职责、依赖和契约不变且风险可界定。

### 5.3 行为保持重构

```text
使用 $development-standards 整理同一模块内的重复格式化逻辑。
本次授权提取私有 helper，保持输入输出、异常、副作用及调用顺序。
不改变业务规则、技术栈、公共契约、模块职责或依赖方向。
先检查实际调用者与风险，合格时走轻量维护并比较重构前后行为。
发现权限、敏感数据、迁移等高风险时，停止受影响实施并说明下一步。
```

行为保持重构的保护测试应在前后实现都通过，不要求制造“旧实现失败”。提取鉴权 helper 即便很小也触及高风险，不能照此豁免正式流程。

### 5.4 增加功能或改变接口

```text
使用 $development-standards 为现有工具增加搜索功能。
先核对现有需求、设计、技术栈及真实确认是否覆盖本次范围。
有效基线直接复用；未覆盖时只补本次受影响的需求和设计。
适用确认完成前不实现，不顺带重选技术栈或重构无关模块。
```

已有有效批准不应反复索要；缺少正式开发基线时只补当前范围，不重写整个产品历史。

## 6. 怎样确认与控制变更

“帮我开发”“你推荐吧”不能冒充对后来生成的需求或选型草案的批准。上下文明确时自然语言确认即可；为方便续接，建议指出文档、内容版本、范围和待决项。

| 情况 | 正确处理 |
| --- | --- |
| 只确认需求 | 进入技术栈/架构讨论，不直接实现。 |
| 只确认技术栈 | 完成并确认本次范围完整设计后再实现。 |
| 仅确认独立 REQ-001 | 其需求、完整设计及必要依赖都确认后可实施；无关 REQ-002 待决不阻塞。 |
| 必要共同契约未决定 | 即使 REQ-001 目标已确认，仍停住依赖它的实施。 |
| 文档自称“已确认”，来源无法核验 | 请用户确认当前内容，不虚构历史批准。 |
| 需求、验收、选型或边界实质变化 | 更新受影响文档、标记相关确认失效，再确认后继续受影响实现。 |
| 拼写、格式、确认元信息或不改变设计的证据更新 | 不自动要求重复确认；也不能借机扩大批准范围。 |

需求变化会影响依赖它的设计确认。只影响设计的变化不应无理由使无关需求失效。部分确认时文档保留按范围区分的状态，不能标为全量批准或全量验收。

完成当前任务不自动扩大提交、推送、PR、合并、发布、生产迁移或外部写入权限；这些操作必须在你的任务授权及项目门禁范围内。

## 7. 客户端与服务端产品

这里的 Agent 是产品客户端或采集端程序，不是大模型。升级或修改 Server，必须保持约定兼容范围内低版本 Agent 的协议、接口、字段语义及核心流程，不能以强制升级 Agent 为既有流程正常运行的前提。

你应提供或与模型讨论：用户/项目认可的版本范围及依据、协议基线、必须保持的流程、可获得的低版本产物、隔离测试环境和证据位置。范围不明确时模型应询问，不能自行淘汰旧版本。

```text
使用 $development-standards 修改 Server 的结果上报处理。
先核对项目规定的低版本 Agent 兼容范围和协议基线；不清楚的事项先问我。
保留旧 Agent 无需升级即可完成的既有核心流程。
记录实际被测 Server/Agent 版本、场景、命令、结果和证据位置。
只测最新版、历史样本回放或全 Mock 不能冒充真实低版本端到端验证。
不兼容、必要验证失败/未运行或证据缺失时，保持相关合并发布门槛未通过。
本次未授权合并或发布。
```

需求和设计获批不能豁免红线；兼容测试通过也不等于获准发布。无法取得充分证据时，可交付说明阻塞项的待审改动，但不能宣称兼容已通过、可合并或可发布。合格局部修复可将兼容记录写在修复说明中，不为记录位置补建历史文档，也不省略验证。

## 8. 检查交付结果

按任务模式和风险验收，不要求每次提交一整套固定表格。至少看清当前阶段、实际改动、适用检查和未解决事项。

| 状态 | 代表什么 | 不代表什么 |
| --- | --- | --- |
| 已确认 | 对应内容版本与范围有真实批准。 | 已实现、已通过测试或已授权部署。 |
| 已实现 | 目标代码已修改或创建。 | 验收和安全检查已通过。 |
| 已验证 | 对应改动的相关检查实际通过。 | 所有场景均覆盖、独立审查或发布已完成。 |
| 已部署 | 有实际执行和部署结果证据。 | 所有业务、安全或兼容目标自动满足。 |

检查报告是否注明通过、失败、未运行、不适用。部分测试通过不能覆盖未验证的验收条件；不清楚原因的失败不能随意称为“既有失败”。没有可运行环境时，应明确“已实现但未完成验证”，不能跳过测试或关闭鉴权、安全检查来制造成功。

正式开发查看需求到模块、实际代码和验收的映射；局部修复/重构查看目标依据、范围和验证，不索要已豁免的两份产品文档。模型自审不能代替项目规定的独立审查、人工审批或 CI 门禁。

## 9. 语言、续接与分享

中英文均使用同一个 `$development-standards`，不需要安装两份技能。规则语言遵循明确偏好，否则中文请求用中文资源、英文请求用英文资源；其他语言使用英文资源并按用户语言沟通。

文档语言可与对话不同：明确指定文档语言优先，其次仓库约定，最后对话语言。

```text
使用 $development-standards，用中文讨论，需求和架构文档用英文。
沿用现有代码标识符，不翻译无关文件。
```

续接任务时说明项目位置、已确认的文档版本/范围、可核验来源、已完成工作和阻塞项。模型应核对内容与确认是否仍对应；真实批准无法核验时，可由你确认当前版本，不必找回丢失的历史聊天。仅切换语言不会使批准失效或授权新的工作。

```text
继续使用 $development-standards。
先核对现有需求、架构和确认记录是否仍覆盖当前范围，再继续安全的已确认部分。
不要只凭“已确认”标签或旧测试结果假定当前版本已批准、已验证。
```

分享时提供整个技能目录，保留两种语言参考、模板、UI 配置和来源署名。手册供人阅读，不需要添加到模型的必读流程。维护规则或模板时成对修改中文源和英文译文；译文冲突不能默默采用更宽松版本，具体以入口的维护规则为准。

## 10. 常见问题

**为什么模型在讨论阶段停下来？**

先看是否有影响当前范围的需求、完整设计、选型或必要依赖尚未确认。停在相应阶段是正式流程的一部分；可以继续讨论和修改文档，不必先写代码。合格局部修复或轻量维护不应仅因缺少历史文档被阻塞。

**模型要求写两份文档，但我只是修一个小 Bug，怎么办？**

要求它用实际调用、数据流、契约及风险解释分类。确实符合局部修复条件时无需追补；若触及权限、数据安全或契约变化，改动小也不能豁免。

**可不可以让模型自己选技术？**

可以让它推荐并解释取舍；你仍需确认提出的具体方案。明确指定部分技术后只讨论尚未决定的关键选择，不要每次重选全部依赖。

**安装了却没调用，或者读错了版本？**

先显式指定技能并要求报告实际读取的 `SKILL.md` 路径及配对修订，检查完整目录、是否禁用以及是否有同名副本。官方文档说明同名技能不合并，更新未出现时可重启 Codex；参见 [本地技能说明](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills)。不要先覆盖安装或修改全局配置来排查。

**能否用“全部同意”一次批准整个项目？**

确认需对应实际已讨论的内容和范围，不能预先批准尚不存在的草案。需求先确认，之后讨论并确认完整设计；技术栈可与明确包含选型的设计一起确认。已获真实、有效且适用的确认直接复用。

**手册能保证模型不会越权或漏测吗？**

不能。技能保持轻量，由模型执行规则；它不替代沙箱、权限控制、CI、安全扫描或人工审查。请以实际工件和证据判断，而不只看模型声称“已遵守规范”。
