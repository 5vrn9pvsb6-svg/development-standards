# 项目需求文档

中文模板源 | [English](../en/requirements-template.md) | 配对修订：`2026-10-05.9`

适用范围：正式开发需要需求文档时使用。合格低风险局部修复或行为保持重构，不因缺少历史文档而要求复制或填写本模板；必要时更新相关已有记录，范围或风险升级则转正式流程。

使用说明：保留仓库已有格式。填写实际讨论结果，删除不适用的栏目并说明重要不适用项；没有依据的信息写入待确认问题，不默认选择“已确认”。编号格式可按项目调整。

## 文档状态与范围

- 文档标识/路径和当前内容版本；项目/功能名称及关联记录。
- 适用范围：本次需求编号、功能边界和主要非目标；部分确认时区分已确认与待决范围，不将整份文档标为全部已确认。
- 当前状态：草案、待确认、已确认或需重新确认，选择实际状态。
- 确认记录：已确认内容版本和范围、真实可核验的用户反馈或项目审批来源；没有时明确未确认，不编造消息 ID。
- 未决项：关联下方问题表，说明有无阻塞本次范围的问题。
- 重新确认触发条件：需求/验收、权限/数据规则等实质改变；记录受影响的旧版本和范围。

文件中的状态标签或版本号本身不是批准证明。排版/拼写和不改变业务内容的证据补充不自动使确认失效；业务变化使相关需求及依赖它的设计确认失效。

## 目标与使用场景

说明目标用户、要解决的问题、当前情况及期望结果。列出主要用户流程和适用角色；区分业务目标与具体技术方案。

## 范围与非目标

列出本次包含、不包含的能力，以及必须保持的既有行为。未来规划不能混入本次验收范围。

## 功能需求与业务规则

每项需求填写一条实际记录；必要时用独立小节补充复杂规则。

| 需求编号 | 用户场景与目标行为 | 输入/输出及业务规则 | 边界/异常 | 验收条件 |
| --- | --- | --- | --- | --- |

验收条件应包含条件、操作和可观察结果，不能只写“正常运行”或“体验良好”。优先复用已有验收编号和测试。

## 约束与非功能要求

仅填写适用项：权限与数据归属、隐私/安全、兼容性、外部依赖、运行环境、性能/容量/可用性目标。需要量化但尚未决定的指标列为待确认，不能编造。

### 技术选型约束与偏好（新项目重点讨论）

记录运行平台、部署环境、预算或资源限制、后续维护人员及能力、既有系统集成、用户明确指定的技术及可接受的取舍。不了解技术的用户可以表达“容易部署”“运行成本可控”等需求，不要求其先选框架；未知条件列为待决项，不编造预算或工期。

这里只记录需求约束与已知偏好，不把模型推荐写成用户决定。需求确认后讨论技术栈选项，将选型结论及真实确认来源记录到架构文档；无需另建一份技术栈文档。

### 低版本 Agent 兼容要求（仅适用于客户端与 Server 通信）

记录需要兼容的 Agent 版本范围及用户/项目依据、协议/接口/字段语义基线、必须保持的核心流程和兼容验收条件。Agent 指产品客户端/采集端，不是 AI 代理。范围未明确时列为待决项，不由模型指定最低版本或排除旧版本。

Server 升级不能以强制升级 Agent 为既有流程正常运行的前提；破坏兼容的变更不得合并或发布。涉及 Agent 交互的变更，必须有对应低版本兼容验证证据；验证失败、必要验证未运行或证据缺失时阻断合并/发布。没有此类通信时说明不适用，不要求创建虚构的兼容矩阵。

## 需求变更记录

记录本次实质变化、影响的需求编号与验收条件，以及是否需要重新确认。不要用修改时间代替真实确认记录。
