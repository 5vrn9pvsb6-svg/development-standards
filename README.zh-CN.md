# 开发要求与编码规范

[English](README.md) | 简体中文

[用户使用手册](docs/user-guide.zh-CN.md)：快速开始、任务示例、确认方式、验收与常见问题；供用户阅读，不增加模型必读项。

双语资源配对修订：`2026-10-05.9`。这是资源对应标识，不是项目批准或验证结果。

`development-standards` 是面向大模型辅助开发的可复用 Skill。正式开发先讨论并确认需求和模块边界，形成项目文档，再进行实现；低风险局部缺陷修复采用轻量通道，不追补历史产品文档。两种流程都将代码改动关联到安全检查和可核验的验收证据。

本 README 是使用说明，不新增执行规则。[SKILL.md](SKILL.md) 是唯一指令入口和语言选择器，[中文核心规范](references/zh-CN/standards.md) 提供完整流程。随附成对的中英文参考与模板，实际执行遵守适用的更高优先级指令。

## 整合的工程实践

它整合了以下工程实践与开发要求：

1. Microsoft 工程流程：需求、设计、验收与完成标准。
2. Google 质量原则：小步修改、可维护性、测试和代码自审。
3. 腾讯代码安全指南：输入、鉴权、数据库、文件、网络及密钥安全。
4. 风险分级与交付要求：高风险变更必须考虑兼容、恢复和验证证据。

这是对公开工程实践与本技能开发要求的选取和整理，不是上述公司的官方统一规范。具体出处与适用边界见 [来源与适用限制](references/zh-CN/sources.md)。

## 使用方式

开始任务时可以显式调用：

```text
使用 $development-standards 开发订单导出功能。
先讨论需求并形成需求文档，等我确认后，再讨论模块与架构并形成设计文档。
两份文档都确认之后再实现。
```

已有项目的缺陷修复：

```text
使用 $development-standards 修复这个缺陷。
先判断是否符合低风险局部修复条件，复用适用的已有记录。
合格局部修复先简述预期行为、依据、范围和验证方式。
不编造批准；合格局部修复不追补历史产品文档，其他情况遵循适用的正式开发流程。
报告实际验证结果和未解决风险。
```

只诊断、不修改：

```text
使用 $development-standards 解释这次失败的原因。
只做只读检查和诊断，不修改代码，不创建项目文档。
```

随附配置允许自动选择技能，但这不保证每个任务都会选择或遵守它；显式调用可以明确所需技能。保留整个技能目录，避免参考文件和模板缺失。

## 语言支持

中英文均调用同一个 `$development-standards`。规则语言优先遵循明确偏好；否则中文请求选 `zh-CN`，英文请求选 `en`，其他语言使用英文资源并跟随用户语言沟通。模型读取一种语言的核心规范，再按需读取相关参考，不加载两套全量资源。这是指令层语言策略，不是安装第二个技能或自动 locale 配置。

生成的每份文档优先遵循明确指定的语言，其次遵循仓库既有文档语言约定，最后跟随对话语言。采用对应中英文模板；其他语言可基于英文模板调整。不顺带翻译无关文件或重命名代码标识符；仅切换语言不使批准失效、改变需求或授予实施权限。

`references/zh-CN` 和 `assets/zh-CN` 是中文规则/模板源，同名英文文件是成对维护的译文，不是两套独立政策。发现差异时报告并核对受影响中文源，不静默采用更宽松译文。英文贡献应同时提出对应中文源修改并说明语义意图，以保持两种版本一致。

```text
使用 $development-standards 处理本任务。
用中文讨论，但需求文档用英文撰写。
保留相同的确认、安全和兼容要求。
```

## 任务模式

| 模式 | 应有行为 |
| --- | --- |
| 只读任务 | 解释、诊断、评审或计划，不实施修改；缺少产品文档不能阻塞只读工作。 |
| 文档工作 | 在批准前讨论、撰写或修订任务要求的文档，不顺带实现。 |
| 轻量维护 | 文字、注释、纯格式、机械修改，以及符合核心规范的低风险行为保持重构；无需新建产品文档，仍检查差异和适用行为。 |
| 局部缺陷修复 | 在可核验的低风险范围内恢复明确的既有预期行为，采用下方修复通道；缺少历史需求或架构文档不阻塞合格修复。 |
| 正式开发 | 新项目、功能、接口变更、不符合轻量维护条件的重构及不符合局部修复条件的行为修改，必须通过两道文档门槛，或复用有效的已确认基线。 |

依据任务实际影响选择模式，不能只按文件扩展名或修改行数判断。已授权的小型重构若保持输入输出、异常、副作用、职责、依赖方向及公共契约，且无高风险影响，可按轻量维护执行并验证重构前后行为；不追补产品文档，也不要求旧实现失败。资格及升级条件见 [核心规范](references/zh-CN/standards.md)。

## 低风险局部修复

本通道用于已授权的既有缺陷修复，预期行为须有明确用户说明、可核验契约或有效验收依据。阅读相关代码、调用者和测试后界定范围与风险；不用于新增功能、改变业务规则、技术栈、模块边界或公共契约，也不用于权限、敏感数据、迁移或其他高风险工作。改动少或被称为“修 Bug”不代表合格。

涉及多个既有模块不自动等于高风险：仍须保持职责、依赖方向和契约，界定授权范围内的调用/数据流影响并做对应验证。不能证明低风险时先澄清或转正式流程，不能借此豁免安全或旧 Agent 兼容要求。

实施前在当前任务、已有 Issue 或修复说明中简述问题与预期、依据、影响范围和验证方式，不强制新建固定文件或两份产品文档。用户已明确预期、范围及修复授权时直接执行，不重复索要需求或设计批准；预期有歧义时先只读检查，再集中询问。复用有效记录；与已确认基线冲突时先澄清，遵守用户或项目更严格的要求。

本通道只减轻文档与重复审批，不免除回归验证、安全检查、低版本 Agent 兼容证据及交付授权要求。未运行或环境阻塞的检查须如实报告；发现范围扩大、需要新增行为或高风险时停止受影响实施，先转正式流程再继续。细则见 [工程流程](references/zh-CN/engineering-workflow.md) 和 [验证要求](references/zh-CN/verification-and-delivery.md)。

## 文档先行流程

以下文档门槛适用于正式开发，不用于合格局部修复或其他不实施开发的模式。

```text
需求讨论 -> 需求文档确认
-> 技术栈（新项目）与模块架构讨论
-> 设计文档确认（新项目含技术栈）
-> 实现 -> 验证与交付
```

1. 讨论目标、用户、场景、范围、业务规则、异常、约束和验收条件，形成或更新需求文档，请用户确认。
2. 基于已确认需求，新项目先讨论技术栈选项，再讨论模块负责什么、不负责什么、接口、依赖方向、数据归属、关键流程和取舍，形成或更新架构文档，请用户确认选型及本次实施范围的完整设计。
3. 只实现已确认范围，遵循项目现有约定及适用的编码和安全要求。
4. 将需求关联到实际模块、代码位置、测试或检查及真实结果，分别报告实现状态和验证状态。

默认项目文档为 `docs/requirements.md` 和 `docs/architecture.md`，优先使用仓库已有文档方式。随附 [需求模板](assets/zh-CN/requirements-template.md) 和 [架构模板](assets/zh-CN/architecture-template.md)。

正式开发的适用确认完成前，允许相关讨论、文档撰写与修订及安全的只读调研，不允许正式实现、测试实现或基础设施变更。已有有效批准无需重复索要。

## 界面设计提供三套方案

涉及新界面或实质重设计时，先交付 **3 套 HTML 视觉原型/示意页面**，使用相同需求、代表性页面和示例数据，具有实质布局/视觉差异，重点关注美观、配色、排版、间距及视觉层级，让用户在浏览器查看后选择，再实施尚未确定的正式界面。每套提供可打开入口和实际渲染检查结果；**静态 HTML/CSS 即可，JS 和交互默认可选**，不要求完整业务流程，用户明确要求时才按指定范围演示。不能只交文字、图片、空占位或换色稿。原型与正式产品隔离，不接真实业务服务；预览和真实选择保存在设计文档，可随架构确认，不代替完整架构批准或产品功能验证。有效既有选择可复用，只读及保持既定设计的修复不强制重选。详见 [工程流程](references/zh-CN/engineering-workflow.md) 和 [架构模板](assets/zh-CN/architecture-template.md)。

## 复杂模块与流程的图示

架构设计阶段，复杂模块必须用架构图、复杂流程必须用流程图表示，随 `docs/architecture.md` 内嵌或关联保存，在提交本次完整架构确认前补齐。图要说明组成/边界/依赖方向，或步骤/分支/结果/关键失败路径，不能只摆组件名称或用占位图替代。图与模块表、接口说明保持一致，不新增独立审批。简单模块、清晰线性流程可用文字/表格；只读和轻量任务不补画全项目图。判定、格式及检查见 [工程流程](references/zh-CN/engineering-workflow.md)。

## 数据库设计文档

数据库设计放在编码阶段：开始编码时检查本次是否使用数据库；涉及时先向用户输出相关设计要点并保存独立文档，再写数据库相关代码，默认 `docs/database-design.md`。新库说明方案；已有库先核对 schema、ORM、迁移和文档，准确覆盖且不变时复用，否则更新或只补当前范围。SQL、ORM 和迁移脚本不能单独替代设计说明。

不要求架构阶段提前生成或批准数据库文档，不新增审批；改变已确认需求、技术栈、公共契约、模块边界或权限/数据规则时仍先确认受影响内容。数据库相关查询修复或重构也输出当前相关设计，不追补需求/架构或整个数据库历史。不使用数据库、纯文字/格式维护和只读工作不触发保存，不能为满足规则越权编辑或访问真实数据库。详见 [工程流程](references/zh-CN/engineering-workflow.md) 和 [数据库设计模板](assets/zh-CN/database-design-template.md)。

## 每次代码变更递增产品版本

每次完整的代码变更都必须递增受影响产品版本，包括 Bug/安全修复、重构、代码注释/格式及测试/脚本修改，轻量通道不豁免。按一次可交付变更计数，不按文件数或同一变更内的重试计数。沿用项目版本规则，交付前更新真实版本入口及必要同步项，报告旧版本、新版本、位置和变化摘要；规则缺失或授权冲突时先确认，不擅自建立版本体系。纯文档和只读任务不触发产品升版；升版不自动提交、打标签或发布，也不豁免旧 Agent 兼容。详见 [工程流程](references/zh-CN/engineering-workflow.md) 和 [交付检查](references/zh-CN/verification-and-delivery.md)。

## 技术栈确认

新项目正式实现前，模型必须与用户确认采用的技术栈。对非技术用户，通常提供 2–3 个真正可行的方案，标明推荐项，用日常语言比较交付成本、部署、维护、扩展与限制，而不只列框架名称。用户已明确指定的技术沿用；只有一个符合约束的方案时解释原因，不凑选项。

需求文档记录平台、部署环境、预算及维护能力等约束；架构文档记录方案、选用组件及适用版本、理由、未决项和真实确认来源。用户可单独确认方案，也可确认清晰写出技术栈的架构文档。用户让模型推荐或代为选择时，模型提出结论和理由供其确认；不懂技术、要求推荐或未回复不等于批准。无需新建第三份项目文档。

技术栈确认不替代需求与本次实施范围的完整架构确认。适用门槛未满足前，不初始化正式工程、安装项目依赖或生成实现代码；可继续讨论与安全的只读调研，探索实验须单独授权。已有项目复用有效选型；实质换栈先解释影响并重新确认，常规兼容补丁不自动触发重新选型。细则见 [工程流程](references/zh-CN/engineering-workflow.md)。

## 确认记录与变更控制

每份文档记录文档标识和内容版本、确认范围、当前状态、真实确认来源、未决项，以及需要重新确认的条件。架构文档还要记录其依赖的需求版本。独立且已确认的范围可推进，不等待无关待决项；必要共享依赖未确认则仍阻塞。部分确认不扩大为整份文档批准，按范围保留混合状态。

需求、验收、权限、技术栈、公共契约或模块边界发生实质变化时，相关确认失效。先更新文档并取得确认，再继续受影响实现。拼写修正、确认元数据和不改变设计的证据补充，不自动触发重新审批。

文件自称“已确认”、代码注释、版本号或内容指纹都不是批准证明。批准应来自用户明确反馈，或项目认可且可核验的审批记录。无法核验旧来源时，请用户确认当前版本，不编造历史。

## 低版本 Agent 兼容性

适用于客户端与服务端通信的产品，Agent 指产品客户端或采集端程序，不是大模型或子代理。Server 升级及代码修改必须向后兼容低版本 Agent，保持既有协议、接口、字段语义和核心流程，不得将升级 Agent 作为这些流程继续正常运行的前提。

兼容版本范围和协议基线由用户或项目规定；不清楚时必须询问，模型不能自行排除旧版本。需求或设计确认不豁免此规则。涉及 Agent 交互的变更必须提供低版本兼容证据；破坏兼容、验证失败或证据缺失时阻断合并发布。兼容检查通过也不授予执行这些操作的权限。

在已有项目文档中记录兼容矩阵；合格局部修复缺少历史产品文档时，可写入修复记录。核验实际 Server/Agent 版本、相关流程及运行结果，不能省略兼容验证。只测最新版或全 Mock 不能证明低版本兼容。设计与证据细则见 [工程流程](references/zh-CN/engineering-workflow.md) 和 [验证要求](references/zh-CN/verification-and-delivery.md)。

## 质量、安全与验证证据

- 优先复用现有框架、成熟库、编码约定和模块边界，限制改动范围，保留用户无关改动。
- 手写源文件保持清晰、内聚的职责；项目长度约定优先，无约定时，本次新增/修改文件超过 **1000 行须评估拆分**，合理拆分或说明保留原因，不机械切割或重构无关旧文件。计数与生成代码、锁文件、第三方代码例外见 [编码约定](references/zh-CN/coding-conventions.md)。
- 按适用性使用腾讯安全基线，检查外部输入、授权、查询、命令执行、文件、外部 URL、渲染、敏感数据、TLS 和资源生命周期。
- 不照搬过时样例，不通过削弱测试、鉴权或安全检查来制造成功结果。
- 核对实际调用、导入和数据访问是否符合模块设计；有现成架构检查工具时复用，否则报告局部自审的覆盖范围。
- 记录真实命令和结果，区分通过、失败、未运行和不适用，以及已实现、已验证、已批准和已部署。

来源包括微软 ISE 工程实践、Google 质量原则、腾讯安全指南，以及 AWS 等公开资料中的交付实践。语言风格存在冲突时以项目约定优先。[来源与适用限制](references/zh-CN/sources.md)说明了具体出处和使用边界。

## 限制与维护

Skill 提供模型行为指引，不是强制执行的安全边界、某家公司的官方制度，也不能替代 CI、安全扫描和人工审批。文档确认不授予超出用户请求的提交、推送、创建 PR、部署或生产数据操作权限。

日常开发只读取相关参考，不加载技能维护用的行为评审判据。修改规则或模板时同步中文源与英文译文、两份 README 和受影响场景，保留必须/建议的强度、模式豁免、确认状态、兼容阻塞及证据标准。检查成对文件名、配置、本地引用及来源署名；行为样本使用语义相同的中英文请求。结构检查或翻译自审不是实际模型行为验证，单次样本通过不能证明所有模型和上下文都可靠。

分享时分发整个 `development-standards` 目录，包括两种语言资源及 `agents/openai.yaml`，不能只发送 `SKILL.md` 或本 README；保留同一技能名。腾讯来源的署名与改编说明须随衍生资源保留，本双语结构不为其他资料声明统一许可证。

维护时沿用入口的“必须/不得/建议、已确认/已验证”术语，并同步入口、两份 README 和资源头部的配对修订标识。标识一致不证明翻译正确，不增加项目审批或日常开发检查；外部来源核对日期与资源修订日期分开记录。
